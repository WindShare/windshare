# Single-Connection Throughput

2026-10-22

Improve useful throughput while keeping link creation, first content, browsing, preview, cancellation, and recovery responsive. Start with one connection; keep the allocation contract valid for multiple direct and relay lanes. Baselines retain the existing Chromium receive-buffer optimization.

## Delivery

Go and browser allocation/capacity ownership are implemented, along with bounded browser Direct ZIP prefetch. Receipt feedback releases unfinished network supply independently of retained output; shared consumers and canceled attempts keep explicit buffer ownership. Regression coverage includes blocked routes, preview fairness, cached/shared output frontiers, retries and lane replacement.

[Implementation evidence](../../testdata/connectivity/webrtc/allocation-20261022/README.md) records complete-file, Direct ZIP, small-file, slow-output, preview/cancellation and reserve-cost measurements, plus browser resume and process-crash recovery. Complete-file throughput improved neither consistently nor conclusively (1 MiB block medians: 19.26 to 18.71 MB/s). Batching and native acceleration are not adopted.

The [readiness follow-up](../../testdata/connectivity/webrtc/readiness-20261022/README.md) adopts browser capacity-transition notifications and demand-owned probe deadlines. Admission scans fall 75%; complete-file throughput remains inconclusive, with no consistent first-output or preview delay established. Transport loss and the earlier retransmission stalls remain under investigation.

## Findings before implementation

- Current production code still reaches 20.33 MB/s for a complete file; the selected Linux socket retains the optimized 2 MiB receive buffer. Chrome background model downloads interfere with repeated measurements. Enlarging the socket removes observed drops but does not eliminate slow rounds; neither output writes nor socket drops alone explain the variation.
- With external DNS blocked only in the test browser, three interleaved 256 MiB pairs gave baseline/batch-64 medians of 16.67/14.30 MB/s, with substantial variation. Paused-output preview medians were 4.95/5.06 s. Earlier fixed throughput-gain and preview-regression claims are unsupported; packet experiments motivate investigation, not adoption.
- Default candidates reproduced asymmetric routing: browser outbound traffic left the LAN for a VPN path, with RTT rising from 4 to 437 ms while incoming file data stayed local. Verify actual selected paths at both endpoints throughout measurements.
- Raising send watermarks to 4 MiB / 90% changed throughput only from 23.07 to 23.25 MB/s, but small-message RTT P95 rose from 64 to 330 ms. Keep the original watermarks and immediate first/tail sends.
- Browser work leaves the public queue before lane capacity admission: a later preview was admitted ninth, versus second in the ownership model. Current-code probes also reproduce unavailable-route work consuming all dispatch slots and stalled bulk output preventing preview admission.
- Direct ZIP currently reads one block, waits for output and checkpoint observation, then requests the next. Broker changes alone cannot supply cross-block parallelism.
- Windows probes confirm explicit cancellation and completion ownership. Concurrent sends can succeed on either side of a failed datagram; successful completions need not form a prefix. Removing the experimental `pion/transport` fork worked, but bypassing `netctx` also bypasses its write serialization and cancellation.

## Design

- **Allocation:** select an eligible work/lane pair and nonblockingly reserve lane and consumer capacity at the broker boundary. Initial, retry, probe, and rescue attempts use the same admission contract; shared content and per-attempt reservations remain distinct. Commit together or roll back; wake on capacity, route, or lane changes. Keep waiting descriptors public and remove private lane task queues. Preserve shared-load cancellation, route authority, preview fairness, output-frontier ordering, and an immediate cold-lane request.
- **Capacity:** receipt replenishes unfinished-response capacity; authentication/output retain reservations until release. Preserve output/cache ownership; charge shared buffers once and independent consumer copies separately. Reserve at admission, with incremental look-ahead. A ready consumer may advance shared work without waiting for a stalled subscriber. Protect a minimal interactive frontier sized for supported block geometry within the existing total budget. Only promptly reclaimable buffers may borrow it; pending network, authentication, and output holdings cannot count as reclaimable capacity. Sustained preview must allow bulk progress; measure the reserve's throughput cost.
- **Datagrams:** preserve ready batches through SCTP, DTLS, and ICE with bounded service turns and no wait-to-fill. Retain congestion control, retransmission, MTU, datagram boundaries, and route/address-family ownership. Use context-aware consumer capabilities through `netctx.PacketConn.Conn()`; ordinary fallback must retain serialization and cancellation.
- **Native I/O:** one send owner per physical endpoint coordinates ordinary and accelerated writes; socket authority retains socket ownership and session/path isolation. Network-generation retirement stops new demand without closing admitted paths. Physical closure stops admission, cancels operations, observes every submitted completion, releases buffers, then closes. Track each datagram; partial failure cannot trigger blind batch replay. Remove old timeout coordination only after its paths use this lifecycle. Platform details stay outside `core`, the broker, and `FrameChannel`.
- **Completion:** distinguish application admission, local I/O completion, remote acknowledgement, authenticated content, and durable output. Canceling a consumer stops its future admission without closing shared lanes or canceling other consumers; accepted SCTP bytes and pending native buffers retain their owners. Persistent resume coverage requires output durability evidence.

## Execution

1. Record a complete-file baseline with browser background traffic controlled, then refactor supply and capacity ownership. Add bounded cross-block prefetch for Direct ZIP while preserving ordered writes, checkpoints, and disk-space bounds. Exercise one lane, mixed direct/relay lanes, unavailable routes, shared consumers, retry/rescue, and lane replacement. Align Go/browser ownership contracts while preserving output semantics and receipt feedback. Multi-connection creation remains independent.
2. Remeasure complete read/seal/transfer/authentication/output workflows before changing the send boundary. Include small files, Direct ZIP, bulk-plus-preview, slow sinks, single-content cancellation, and actual resume/crash recovery. Profile the remaining bottleneck for the selected block geometry and hardware. Compare first content and interaction delay alongside throughput; use bounded session/path/operation traces for queue wait, submission, completion, and output retention.
3. Prototype portable batching only where profiling supports it; adopt it only if complete-workflow gains repeat. Preserve immediate first/tail sends, control traffic, and ordinary-write serialization/cancellation. Replace the experimental shared-deadline adapter before adoption. Keep dependency patches reproducible; remove experimental switches and avoid toolchain changes.
4. Evaluate native acceleration through the same send owner only if a bottleneck remains, measuring its incremental benefit over the portable path. Exercise submission/cancellation races, non-prefix completion failures, shutdown, and path replacement. Retain it only when complete-workflow gains justify its maintenance cost.

Deliver allocation/capacity changes independently; batching and native acceleration are optional. Count SCTP/DTLS patch maintenance and platform lifecycle complexity even after removing the experimental transport fork.
