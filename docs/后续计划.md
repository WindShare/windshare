R 生产入口已经采用 suite `0x02` 的即时 descriptor、渐进 catalog、file-local content、ProtocolSession、
plan-specific receiver output，以及 activation 时 relay 立即可用、P2P 后台有界恢复的连接语义。后续实现不得破坏以下基线：

- 出链接只验证所选根，不枚举后代，不预读内容或预哈希。
- 中转不持有内容密钥，不获取文件名或明文内容。
- catalog/content 协议只依赖 `FrameChannel`；传输适配器不拥有身份、调度或 UI 策略。
- `core/**` package 不依赖非 core 的 WindShare package；CLI、各桌面端和移动端必须复用同一应用能力，不能复制业务流程。
- 分离密钥保持可选，默认仍是一条完整能力链接；内容起传由用户操作触发。`auto` 允许认证浏览后的单次有界 ICE 预热，不做映射；`relay-only` 保持零 ICE、STUN 和映射。
- 单一根模块是唯一生产发布单元。CI 从完整 package 集合动态生成互不重叠的 core 与 non-core
  集合；根发布对同一精确提交的归档执行 Linux/Windows 检查后，只创建不可移动的 `vX.Y.Z` tag。
  本地 `make ci`/`make ci-full` 验证当前源码，发布流程另行认证已提交的根模块归档。

所有 durable output identity 必须锚定冻结的 `OperationID + ReceiveIntentDigest + materialization binding +
FileID + FileRevision + canonical artifact path + exact size + authority/owned object`；`TransferJobID` 与
`OutputSessionID` 只标识一次运行。目录页由
`DirectoryID + Generation + PageIndex` 定位，内容由 `FileID + FileRevision + LocalBlockIndex` 定位。
`PeerPathID` 只标识一个 ProtocolSession 内的 direct recovery path；每次协商使用新的 `AttemptID`、operation 与
grant。channel 建立后经 `LaneID/LaneEpoch` 进入 session；这些 identity 都不能进入 catalog、内容缓存或
ReceiveIntent/FileCheckpoint 恢复身份。

## 3. M2 — Windows 桌面

### 3.1 完成定义

M2 完成时，Windows 用户可以从资源管理器或桌面应用选择文件/文件夹，立即得到分享链接，
管理在线分享，也可以粘贴链接接收并续传。CLI 与 GUI 复用同一套 engine 代码，并直接复用当前生产实现的
descriptor、catalog、ProtocolSession、file-local content、ReceiveIntent、plan-specific output、
`FileCheckpointV2`、receive lifecycle/recovery 和 suite `0x02`。UI 不得重定义 wire 或 receiver-local canonical contract。

M2 复用现有多 relay 并行能力；不包含 macOS/Linux 客户端、移动端、离线寄存、账户、链接撤销/次数限制、
TURN、padding 或公网正式运营。
签名内容的原样重放仍是已知残余，由 M4 的签名 `expiresAt` 关闭。

### 3.2 engine 与桌面边界

- `engine/` 是分享、接收、续传、连接编排和生命周期的共享原生入口，位于 `cmd/**` 和网络无关的
  `core/**` 之外。M2.1 将现有 CLI 接入这一入口，统一连接恢复、会话换代、内容准入和输出结算。
  engine 实例持有任务状态及跨任务的目录、内容缓存和文件版本总预算；CLI 保留参数、展示和退出码映射。
  桌面端以后在自身进程中持有独立 engine 实例，默认中转等基础配置可共用。
- M2 在线分享随 engine 进程存活；明确 `Stop` 或退出必须拒绝新 join、终止活动下载并注销 relay，
  只有意外断线可进入具名恢复宽限。
- plan-specific output runtime 只执行 frozen ReceiveIntent；`FileCheckpointV2` 是唯一 durable have-state。
  Native ordinary state 只在用户指定的目标根内做 active lookup/list/discard；Web repository 仍由 output authority
  独占。CLI/GUI 不得自行推断 durable ranges、把 workspace 当 destination 或另造 journal。
- 文件源通过 `liveshare.FileSourceFactory` 注入；osfs 解释本地路径，core 保存不透明的源引用。
  文件源持有本次分享使用的句柄和授权租约，等待目录/内容工作结束后释放；真实移动端提供者随 M3 接入。
- M2.2 的 Flutter 启动层通过 `dart:ffi` 调用薄 C ABI 的 `Start/Stop`。`Start` 在本机监听就绪后返回随机端口和
  每次启动随机 bearer token；token 不落盘、不进入环境变量，认证失败立即断连。
- 本地 WebSocket RPC 使用带 `id` 的 JSON 请求/响应和事件推送；进度事件节流。文件数据面不经过
  FFI 或 RPC，避免复制大块数据和扩大内存所有权边界。页面销毁或 RPC 断连不隐式取消 engine 任务。
- engine 负责取消、明确停止、正常关闭、错误分类和类型化观测；时钟、随机源、存储和网络均可注入测试。
  CLI 负责诊断投影与格式化。任务结果独立于有界观测队列，订阅结束不取消任务，最终状态在生产者与资源清理完成后结算。
- engine/RPC 契约保持平台中立；路径、shell 激活、打包和凭据存储由各平台适配器负责，不能把
  Windows 语义泄漏进共享领域模型。
- Windows shell 集成只传递用户选择并激活应用，不在 Explorer 扩展进程内启动分享或持有密钥。

### 3.4 M2 对外交付边界（按需）

以下记录对外交付时需要确认的产品结果与证据。开发期间继续执行相关门禁；只有决定发布时才整理发布记录并运行发布流程，M2 开发完成不以发布为条件：

1. 持链攻击回归证明：攻击者拥有 `readSecret` 仍不能伪造 descriptor、page、block、error 或 terminal，
   也不能在诚实 relay 注册发送端路由；真实签名内容的过期重放明确记录为 M4 前残余。

   明确停止/退出另须证明活动下载被终止、路由不可恢复且资源全部清理。
4. `--relay-only` 与 GUI 同名选项都阻止 offer、answer、candidate 和 ICE 收集，同时 relay 下载可用。
5. 资源管理器单选/多选、应用已运行/未运行、安装/卸载四类 Windows 路径均有自动化或可复现实测。
6. `make ci` 全绿；Flutter analyze/test、Windows GUI E2E 和安装包 smoke test 已进入 CI，而非仅本机通过。
7. core package 集合总覆盖率 ≥90%、non-core package 集合总覆盖率 ≥80%、每包 ≥70%；新增 Dart 领域/RPC 代码有单元测试。
8. `docs/releases/M2.md` 简洁记录支持范围、相关 workflow run、benchmark 环境和安装包校验；
   原始诊断留在对应 CI run，不塞回本计划。

## 4. M3–M5 边界

### M3 — 跨平台客户端

- M3 分为桌面移植与移动端两条可并行交付线；复用 M2 engine、`dart:ffi + 薄 C ABI` 启动接口和同一 Dart RPC 客户端。
  桌面与 Android 使用 `c-shared`，iOS 使用 `c-archive` 链接打包；移动端原生宿主管理系统生命周期与文件授权。
- macOS/Linux 桌面端复用 Windows 已完成并验证的分享、接收和续传流程；平台适配器只负责文件选择、
  应用激活、系统集成与打包，不持有业务规则或内容密钥。
- macOS 覆盖 Finder/系统分享入口、签名、公证和沙箱文件访问；Linux 覆盖 XDG portal、主流桌面环境
  集成及明确的软件包/发行版支持矩阵，不能笼统宣称所有 Linux 环境均受支持。
- Android/iOS 接入系统分享面板、文件选择器、后台/前台切换、移动网络与存储权限；iOS 后台限制
  必须以真实设备验证。
- 密码档 suite 仍是可选决策。只有“可口述/可记忆”价值经用户验证成立才引入 Argon2id；不能以其
  替代 128-bit 分离密钥，也不能降低抗离线爆破参数。
- 发布边界：macOS/Linux 的声明支持矩阵均完成安装、卸载、分享、接收、续传和 CLI/浏览器互操作；
  Android/iOS 各至少一台真实设备完成分享、接收、暂停恢复、进程切换和互操作测试。

### M4 — 离线模式

- 中转支持有期限的密文寄存、账户/API Key、配额、保留策略与明确计费边界。
- 上传 authority 与读取 capability 分离；接收者不能取得修改、撤销或续期权限。
- 未原子提交的 staging/inventory 对 receiver 不可见，失败或停止只清理 ownership-proven staging。
- 寄存服务只能保存 E2EE、sender-authenticated content objects 与完整性 inventory，不能取得内容密钥、sender 私钥
  或保存 ProtocolSession/OperationID/Lane envelope。
- commit、expiry、撤销、下载次数限制和 delivery identity 必须有认证语义，且不能改变已验证的 FileID/FileRevision ranges。
- 具体 suite、对象 schema、inventory 树、账户和计费模型在 M4 产品需求明确后设计；当前 suite 的 unused flag、
  capability bit 与曾设想的 `OfflineCommit` 形状都不是实现前提。
- 发布边界：上传中同一链接可在线下载，commit 前退出会失效，commit 后退出及活动下载可切到寄存服务；
  越权续期/撤销、源漂移、部分提交、过期重放、配额竞态和清理失败均有对抗测试。

### M5 — 生产扩展与上线

- 多 relay 与边缘部署由 relay 专项计划维护。M5 消费其结果，不另造内容或会话身份。
- 若连接专项获批，多节点仍以同一 `pkHash + ShareInstance` 验证 descriptor 与注册 proof，节点 resume token
  独立；`PeerPathID/AttemptID` 只描述协商，FrameChannel 仍通过 `LaneID/LaneEpoch` 接入同一 ProtocolSession。
- 区域内 L7 按公开 share route 一致性哈希；支持 drain、容量指标和零停机重注册/续传。
- 评估 TURN、padding、请求隐藏及逐块去重；没有明确威胁或容量收益的功能不进入协议。
- `windshare.top` 上线前必须完成举报/禁用 shareId、速率与配额、ToS、监控告警和 egress 成本模型。
- 发布边界：容量、故障切换、安全、滥用响应和成本预算都有可复现演练，才能声明 production-ready。

## 5. 持续门禁与维护规则

- 迭代使用 `make check` 或聚焦 gate，推送前运行 `make ci`；开发环境负责预装工具、Web 依赖和浏览器。
- `make long-go` 与自动 weekly workflow 负责长 Go、durable、网络、interop、跨浏览器和 Windows 浏览器路径；
  根模块发布流程负责精确提交归档和原生文件系统认证。具体入口见 [`validation.md`](validation.md)。
- 新 UI 不得直接依赖 CLI internal 包；重复业务流程视为 engine 边界缺失，优先重构根因。
- 本文不记录逐次评审对话和版本流水账。完成一个里程碑后，只保留一行结果，详细材料归档；
  下一里程碑才展开为任务表。决定对外发布时再维护简洁发布记录。
- `✅` 表示里程碑范围内的能力已实现，端到端路径与必要验证已通过；代码合并本身不代表完成，
  对外发布也不是开发完成或开始下一里程碑的前置条件。
