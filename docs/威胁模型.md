# WindShare 威胁模型

> 状态：suite `0x02` 当前生产安全边界。本文定义需要长期成立的安全性质，不规定产品交互、平台覆盖或具体实现。
> 当前生产范围是 `LiveOnly`；协议机制见[协议规范](协议规范.md)，产品语义见
> [原始需求](clarifications/原始需求.md)，验证责任见
> [Validation](validation.md)与[跨运行时向量](../core/testvectors/README.md)。

## 0. 文档维护原则

- 只记录受保护资产、攻击者能力、信任边界、安全不变量、非目标和残余风险。
- 规则描述“必须防止什么以及为什么”，不固定“具体怎么实现”。新增规则若不能指出对应威胁、资产和缺失后的安全后果，就不属于本文。
- UI 流程、产品默认值、平台支持、容量与时间常量、错误码、状态机、存储布局和当前能力限制不得写成安全不变量。
- 本文只保留理解安全边界所需的机制假设。
- 当前实现方式不得自动升级为永久约束。新方案只要保持本文不变量，就不需要修改威胁模型；改变信任边界或安全承诺时，才同步更新本文、协议规范和验证材料。

## 1. 范围

### 1.1 保护目标

- relay、网络和恶意持链者不能读取未授权内容、伪造 sender 身份或取得其他 receiver 的 session。
- 文件名、精确大小、文件标识和操作语义不以明文协议字段暴露给 relay。
- receiver 得到的 catalog、文件 revision、控制消息和终态可验证来源与上下文，不能被跨分享、跨 session 或跨作用域剪贴。
- sender 提供的名称、媒体和内容均按 hostile input 处理，不能越过 receiver 选择的输出根或取得本地输出权限。
- 已验证内容不能在不同 revision 间静默拼接；恢复、发布和清理不能从 UI 状态、同名路径或不确定证据制造权限。
- 未认证输入造成的资源占用必须有界，故障不得无必要地扩大到无关分享、session、文件或输出任务。

### 1.2 非目标

- 恶意 relay 或网络可以永久拒绝服务；本文不承诺可用性、匿名性、padding、固定速率或流量隐藏。
- 能力链接是 bearer capability。取得完整链接的人被授权读取并可继续转发；当前不提供 receiver 身份认证或泄漏后撤销既有读取能力。
- 同一 OS 账户下恶意本地进程的主动篡改、供应链攻击以及密码库、浏览器和文件系统实现缺陷不在保护范围内。
- 本地正常并发修改、rename、权限变化和空间不足属于产品正确性输入；它们不得导致越权、静默内容换代或误删陌生对象。

## 2. 能力链接与信任边界

能力链接预期经群聊等半公开渠道流转。fragment 是消息文本的一部分，聊天平台、预览机器人或截图取得完整链接后，在密码学上就是持链者。产品可以支持将 `#` 后密钥与 URL 分渠道发送；fragment 必须在任何网络、日志或持久化工作开始前从页面地址中移除。

| 角色 | 信任与能力 | 安全边界 |
|---|---|---|
| relay | 不可信；可延迟、丢弃、重排外层流量 | 可见路由所需身份、sender 公钥、连接标识、IP、密文长度/时序/总量；不得见文件元数据、内容或内层操作语义 |
| 持链者 | 被授权读取，可能恶意并与 relay 合谋 | 可解密 sender objects、建立自己的 session；不能伪造 sender、控制 route 或派生其他 receiver 的 traffic key |
| sender | 内容权威，不受 receiver 信任用于本地输出 | 可签名恶意名称和内容；不能授权越过 receiver 选择根、覆盖范围或本地生命周期 |
| receiver | 受用户信任保存能力和表达本地选择 | 仍须把 sender 数据、媒体和路径作为 hostile input |
| offline delivery | 当前不存在；未来仍不可信 | 只能保存和投递 sender-signed transport-neutral objects，不得取得解密密钥、sender 私钥或 session envelope |
| 本地源与输出对象 | 可变的正确性输入 | 变化可使操作失败，但不能扩大网络或本地权限 |

## 3. 安全不变量

### 3.1 Sender authenticity 与 route authority

- link 必须锚定完整 sender public-key identity；截断路由标识发生碰撞时不得覆盖或取得既有 route。
- 持链者拥有 `readSecret`，因此仅有 AEAD 不足以证明 sender。sender objects、session control 和 terminal 必须使用相互隔离的签名上下文，并绑定其分享、对象、session、方向和作用域。
- route 注册、恢复和停止必须使用新鲜 sender proof，并绑定 relay identity、分享实例和具体动作。旧 proof、已停止身份或其他 relay 的 proof 不能重新取得 authority。
- 相关 ID 只用于关联；任何 OperationID、路径名、错误文本或 UI 状态都不能单独成为生命周期或权限依据。

### 3.2 Session confidentiality、隔离与 replay

- receiver 必须在昂贵资源分配前证明持有 capability；握手必须认证 sender 并为每个 receiver 建立独立 session secret。
- traffic key 和认证上下文必须区分 session、lane/epoch、方向和 sequence。跨 receiver、跨 session、跨方向或旧 epoch 的密文不能被接受。
- connectivity negotiation 必须保持 E2EE；未认证或跨作用域输入不能诱导实现签名、反射或升级为其他操作的 terminal。
- replay 防护不能依赖可伪造的关联 ID。一次性授权、旧 channel 和迟到回调不得重新取得已经消费、替换或撤销的 authority。
- 被动链接预览或自动页面加载不得触发地址暴露或无界 P2P 工作。何种用户动作构成授权、尝试并发和恢复预算属于产品与连接策略，不由本文固定。
- direct-path 故障不得关闭健康 relay 或扩大 ProtocolSession terminal，除非存在经过认证且确属该作用域的不安全状态。
- 临时密钥擦除后，session traffic 与 control 应获得前向保密；由长期 `readSecret` 保护的 sender objects 不宣称 PFS。

### 3.3 Catalog、源对象与 revision 一致性

- catalog generation、page、terminal、directory error、file revision 和 block 必须认证来源、顺序、完整性及所属分享，不能发生 gap、splice、旧实例替换或 terminal 后追加。
- 一个已认证的 directory generation 和 file revision 是不可变身份。源内容变化必须失败旧身份或产生明确的新认证身份，不能静默换代。
- 同一 revision 的所有范围必须来自一致的 source evidence。无法证明仍是同一 revision 时，不得签发新读取权限，也不得把旧 verified ranges 搬到新 revision。
- 稳定性可以由排除写入的 handle、可靠版本证据、snapshot 或其他可审计机制提供；本文不强制具体方案。任何持久内容副本都必须由产品明确授权、展示成本，并承担与源内容相同的保密和清理责任。
- sender 必须从受约束的源根和已认证对象身份解析请求；receiver 提供的路径或名称不能成为源文件访问 authority。
- catalog、scan、entry、memory、handle、lease、cache 和 reassembly 等资源必须在取得前进入有界预算；单个 receiver 的取消或耗尽不能撤销其他 receiver 的合法资源。

### 3.4 Receiver output、恢复与本地权限

- 本地输出 authority 必须来自 receiver 的明确选择，并绑定选择内容、产物语义、目标范围和具体 operation；sender、relay、路径字符串或 presentation state 不能扩大它。
- 所有 path segment 和 archive entry 必须使用统一 canonical policy，并从受约束的 root/handle 派生。absolute path、`..`、separator alias、symlink/reparse 绕过、重复或冲突 entry 必须拒绝。
- 不得静默覆盖、合并或认领已有对象。本文不规定产品是否提供 Replace、Merge、Skip 或 Keep Both；任何已有对象 mutation 都必须取得清晰、限定范围且仍然有效的用户授权。
- compatible-name 映射必须无歧义、抗碰撞并对用户可见；本文不规定浏览器异常、操作系统、脚本或具体恢复方式。
- cleanup、discard 和 expiry 只能删除 ownership-proven unfinished state。已发布对象、陌生对象或 ownership 不确定对象不得删除或按名称认领。
- durable have-state 必须来自绑定 exact operation、intent、FileID、revision、canonical path、authority 和 owned object 的认证 checkpoint。progress、preview cache、成功 Write 或 aggregate manifest 不能制造 verified ranges。
- revision、ownership 或 checkpoint conflict 应限制在依赖该证据的最小安全作用域；只有共享 root、registry、lease 或 operation authority 不确定时才能扩大阻塞范围。
- complete artifact 只有在完整性得到验证后才能标记成功或发布；prefix-visible artifact 必须明确呈现 partial 状态。browser handoff 只能证明浏览器已接管，不能证明用户已经保存。
- 文件系统或浏览器能力只限制产品可以承诺的 publish、resume 和 cleanup 语义，不能被写成平台白名单。能力不足时不得虚假宣称保证；是否提供明确降级由产品文档决定。
- 签名媒体仍是不可信输入；解析、解码、内存和 codec 使用必须有界，preview cache 不能成为 checkpoint 证据。

### 3.5 资源、撤销与故障范围

- 长度、fragment 数量和结构必须在分配前验证；operation、session、share、process 和持久安全状态都必须有界。
- anti-replay 与 revocation 状态可以过期、压缩或换代，但回收不能使旧消息、旧 route、旧 session ID 或旧授权重新有效。
- 资源耗尽必须拒绝最小必要作用域的新工作，不能以无限持久状态换取安全，也不能让一个参与者无必要地耗尽无关参与者的容量。
- malformed、stale 或 unknown input 应在能够保持共享通道同步与权限边界的最小作用域失败；只有连接本身的认证或 framing 无法继续可信解析时才升级为 connection-fatal。
- observer、日志、错误文本和诊断可用性不参与协议、重试、路由、settlement 或本地权限决策。

### 3.6 诊断与遥测

- 自动遥测不得包含文件元数据、capability、secret、credential、文件内容或可恢复应用明文的 raw protocol data。
- 默认本机日志可以记录有界的操作标识、阶段、决策原因和原始错误，以便重建运行路径，但不得授予或持久化读取能力。
- 用户主动生成的敏感诊断包可以包含明确列出的路径、IP、连接或协议诊断；导出前必须提示内容与分享风险，并把诊断包作为敏感数据处理。capability、`readSecret`、sender private key 和文件内容始终不得记录。
- 诊断数据的存在、缺失、截断或导出失败不能改变安全或产品结果。

### 3.7 在线生命周期与未来 offline delivery

- 当前生产只声明 `LiveOnly`：发送端明确停止后，旧 route 和活动服务必须失效，停止消息或旧注册 proof 不能被重放为恢复。
- 意外断线后的恢复必须重新证明 sender authority 并保持相同分享身份；grace 时长和恢复策略不属于本文。
- 未来 offline delivery 只能保存 sender-signed transport-neutral objects 与完整性 inventory，不得取得 `readSecret`、sender 私钥或 session envelope。
- offline 内容只有在完整 inventory 原子提交后才能对 receiver 可见；过期、撤销和重新提交必须有认证语义，不能让未提交或已撤销内容复活。

## 4. 已知泄漏与残余风险

- relay 仍可观察路由身份、sender 公钥、IP、连接图和密文长度、时序、总量，从而推断文件大小或操作模式。
- 完整链接仍是读取能力；转发、截图或聊天平台扫描会把读取权交给新的持有者。分离密钥只能降低单渠道泄漏风险。
- sender-signed 对象可能在其有效分享上下文内被原样重放；session、generation、lease 和 terminal 上下文限制其作用。
- source provider 错误复用版本证据，或文件在 handle gap 内修改后恢复相同 fingerprint，可能无法检测；没有选择 snapshot/content-hash 的模式不宣称相应保证。
- 恶意 sender 可以提供恶意但签名的名称、媒体和内容；签名只证明来源，不证明内容安全。
- 同一 OS 账户下恶意进程可篡改本地日志、checkpoint、sidecar 或输出；本文只要求实现不利用覆盖或删除去“修复”无法证明的 ownership。
- 密码算法、WebCrypto、OS locking、persistent handle、filesystem durability 与依赖供应链的实现缺陷仍需平台和互操作测试。

## 5. 验证责任

- Go 与 TypeScript 必须共享认证上下文和篡改向量；改变分享、对象、session、lane、方向、sequence、operation 或 fragment 上下文必须失败。
- relay-view 验证只能看到公开路由信息和密文特征，不能取得文件元数据、内容或内层操作语义。
- adversarial resource 验证必须覆盖认证前分配、fragment、catalog、session、cache、撤销状态和故障隔离。
- output 验证必须覆盖 root confinement、archive traversal、明确 mutation authority、ownership-scoped cleanup、revision 隔离和 truthful publication。
- telemetry 与诊断验证必须分别覆盖默认禁止项、用户授权的敏感导出边界，以及诊断不参与 authority。
- 具体测试集合、平台证据、容量和时间参数只在[Validation](validation.md)维护，避免把测试实现反向固化成安全模型。
