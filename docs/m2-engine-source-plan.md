# M2 共享 Engine 与文件源边界：CLI 重构计划

## 目标

当前已进入 M2。本计划在保持现有产品行为的前提下，通过现有 CLI 落地共享 engine 和文件源边界：提取分享、接收、恢复和关闭流程，接通可注入的文件源，并让 CLI 成为这套能力的首个实际使用者。实施围绕 Go 应用编排、core 消费侧契约、osfs 适配和 CLI 调用展开。

Windows 上现有 CLI 与 osfs 的接口、句柄和文件版本实现随重构一起维护。Windows 桌面界面、Explorer 集成、Flutter/RPC 和 Android/iOS 适配随各自客户端开发推进；本计划先把它们将来复用的能力落实到 CLI。

保持日常操作直接顺畅：选中文件后立即获得链接，逐步浏览目录，连接失败后保留已完成的下载进度。本地磁盘文件继续使用原生读取，无需额外复制整个文件，也无需提前遍历目录。

Android 文档选择返回带授权的 URI，通过内容提供者访问。提供者可能暴露远程文档或虚拟文档，访问权限也可能失效。返回的文件描述符还可能对应无法随机定位的管道。这些差异由文件源设计处理，独立于启动方式。这里将其作为设计依据，当前实现以 osfs 和非路径测试源推进。相关说明见[文档访问](https://developer.android.com/training/data-storage/shared/documents-files)与[ContentResolver](https://developer.android.com/reference/android/content/ContentResolver)。

## 应用结构

在 `cmd/**` 和 `core/**` 之外引入 `engine/`，作为共享的原生应用入口，组合现有 core、connectivity 和 transport 组件。

| 组件 | 职责 |
| --- | --- |
| Engine 入口 | 创建分享和接收任务，提供任务状态、结果及类型化观测事件，处理取消、明确停止和应用关闭。 |
| 分享编排 | 管理分享生命周期、准备后的发送端、中转准入与恢复，以及有序释放。 |
| 接收编排 | 管理接收意图、输出操作、连接代次、内容准入和任务结算。 |
| 现有 core 模块 | 管理目录、协议、文件版本、调度、接续和输出事务语义。 |
| 现有原生适配器 | 通过 osfs 获取所选文件源和输出目标，管理操作系统句柄，并注入具体存储和网络依赖。 |
| CLI 适配器 | 将命令参数转换为 engine 请求，将 engine 结果转换为终端展示和退出码。 |

保持 engine 公共入口精简，将分享和接收实现在职责集中的内部包中。在消费侧定义小接口，注入时间、随机源、文件源与输出构造，以及连接创建能力。共享容量协调由 engine 实例持有，每次分享和接收的状态归对应任务所有。

CLI 与桌面端复用同一份 engine 代码，并在各自进程中持有独立实例；任务状态和生命周期由各自实例管理。默认中转等基础配置未来可以共用，本次沿用现有配置行为。

CLI 在进程内直接调用 engine，文件字节继续通过原生内容与输出流程传输。以后接入桌面 RPC 或移动端时，由对应适配器消费相同的应用 API，并提供本平台的文件源。浏览器继续使用 TypeScript 运行时和共享协议契约。

## 文件源模型

### 文件选择与资源所有权

将发送端只接受路径的输入，替换为平台装配层提供的文件源工厂。CLI 路径适配器使用 osfs 构造该工厂。

工厂将所选对象绑定到一次分享，并接收建立根节点和节点身份所需的目录上下文。工厂返回一个资源所有权明确的文件源，通过现有消费侧契约提供所选根节点的元数据、渐进目录发现和文件版本打开能力。启动时获取所选根节点的元数据，后代节点和内容按需访问。

文件源负责释放其底层句柄和本次分享持有的授权使用租约。每个已打开的稳定文件分别管理自己的关闭生命周期。发送端释放资源时，先等待使用这些资源的目录与内容工作结束，再释放文件源。准备失败时也遵循同样的资源所有权关系。

平台继续负责申请操作系统权限和管理持久授权策略。结束分享时释放本次对文件源的使用，不直接撤销其他任务仍在使用的权限。授权被撤销或对象缺失时，返回类型化的文件源错误，供 engine 展示和记录 trace。

### 对象定位与内容身份

将用户可见的目录路径，与打开源对象所用的私有引用分开。将私有定位信息调整为绑定到所选范围的不透明对象引用。osfs 将自己的引用解释为受根目录约束的文件系统位置，文档提供者则可以使用文档标识符。

同步调整目录请求、私有目录存储和内存用量统计。保留源对象身份与版本证据之间已有的区别。接收端路径和协议文件身份继续描述共享目录，独立于宿主平台查找对象的方式。

复用 `RevisionSource`、`StableFile`，文件源封装须保留 `RevisionContinuitySource` 的连续性语义。适配器提供发布目录所需的元数据，以及内容传输所需的精确大小、按偏移读取能力和同一版本证据。元数据未知时明确报告，不填入看似合理的值。

URI 可读或文件描述符支持随机定位，都不足以单独证明内容稳定。文件源无法提供所需语义时，沿用现有错误处理和资源释放语义，由 engine 返回类型化结果，CLI 保持现有展示与退出行为。原生本地文件保持当前的直接访问方式。

## 执行顺序

### 1. 建立文件源契约并迁移 osfs

- 在 liveshare 装配边界增加消费侧文件源工厂和资源所有权契约，复用目录与内容接口。
- 一并重构私有源定位、存储表示和 osfs 映射。文件源授权仍限定于原始所选范围。
- 调整发送端准备和资源释放流程，使其持有注入的文件源。从共享发送端装配中移除具体文件版本源字段和内部 osfs 构造逻辑。
- 调整 CLI 路径选择逻辑，使其构造 osfs 文件源工厂，并更新发送端调用位置。
- 迁移相关文件源和生命周期测试。以不透明对象标识的非路径测试源走同一套 sender 准备与读取流程，覆盖按需发现、范围读取、版本变化、授权失效和资源释放，并验证跨打开稳定与仅句柄内稳定两种源的关闭重开行为。

### 2. 将接收编排提取到 engine

- 将 `get.go`、`get_transfer.go` 以及准入、peer 和恢复辅助代码中的接收编排，迁移到接收实现中。
- 复用 `receivercontinuation` 协调会话换代。由 engine 管理各代会话使用的具体连接资源的创建和释放。
- 连接变化时，接收意图、输出操作、已完成的数据范围和进度统计继续归属于原任务。
- 通过消费侧接口提取输出装配，保留现有 osfs 输出实现。将恢复和续传命令辅助代码中的业务决策迁出，交互选择与终端格式化继续留在 CLI。
- 将编排内部的 CLI 退出码和命令专属结果发布依赖替换为类型化应用结果，一并迁出 `commandprojection` 中的成功条件、部分完成和故障归类。CLI 保留展示及退出码映射。
- 将针对恢复、准入和结算的测试迁移到对应模块，通过注入连接创建能力和时间，构造可重复的故障序列。

### 3. 提取分享编排并统一应用资源归属

- 将发送端准备、中转装配、可用性处理、分享服务和结算从 CLI 迁移到分享编排。
- 使用第 1 步建立的文件源工厂。由 engine 实例持有进程级文件版本容量协调器、目录预算和内容缓存预算；各分享保留自身额度并归还占用，沿用现有耗尽策略。
- 保留明确停止分享时的行为：冻结新准入、结束活动会话、停止路由恢复、释放注册，并在释放文件源句柄和密钥前等待依赖这些资源的工作结束。
- 为任务取消和应用关闭安排独立于已取消调用方上下文的清理时间。最终结果保留清理失败信息。
- 将 CLI 的 share/get/resume 操作接入 engine，每迁移一项流程，就移除被替代的 CLI 业务实现。

### 4. 整理 engine 结果与 CLI 观测接入

- 由 engine 提供 CLI 实际使用的类型化请求、任务状态、结果和有界观测事件。复用现有观测基础设施，以及稳定的分享、操作和会话标识符。
- 将终端展示和日志订阅与任务执行分开。订阅结束只释放观测资源；CLI 将 Ctrl+C 等用户操作显式映射为任务取消或 engine 关闭。
- 在任务创建、文件源获取、会话换代、准入决策和结算时输出结构化 trace，包含相关标识符和决策上下文。
- 保持最终结果的发布顺序：各生产者结束工作、资源完成释放后，再结算任务状态。进度展示可以合并更新，终端输出缓慢不阻塞内容传输。

### 5. 通过 CLI 场景完善新边界

- 让现有 CLI 分享、接收、续传、取消和关闭场景经过新 engine，关注会话替换期间的进度保留、输出资源归属和最终结果。
- 结合现有 osfs 测试与非路径测试源，检查源引用解析、稳定读取、能力不足时的错误，以及关闭期间的资源释放。Windows 上继续使用并检查现有 CLI/osfs 的原生能力。
- 利用已有测量方式，对比重构前后的出链接时间、内容起传时间、传输吞吐和临时空间占用。新增测试集中于资源所有权和并发行为，覆盖跨分享总量限制、独立释放及准备失败回滚，减少重复的长时间端到端场景。
- 更新受影响的包与 API 说明和路线图条目，使其反映实际的职责归属和执行顺序。

## 后续客户端衔接

桌面或移动客户端复用同一份 engine 代码。Flutter 通过 `dart:ffi + 薄 C ABI` 调用 `Start/Stop`，业务请求与事件走带认证的本机 WebSocket RPC，文件数据不经过 FFI/RPC。engine 生命周期独立于页面和 RPC 连接。Flutter 启动层/RPC、Windows 桌面与 Explorer 集成、Android/iOS 文件源与原生生命周期适配随对应客户端开发推进。

非路径测试源能够暴露共享代码对磁盘路径的依赖，也能模拟访问失效和版本变化，但不能证明真实文档提供者的权限、描述符和内容稳定性行为。接入 Android 时，再用小型文档选择器实验检查这些行为；提供者支持直接读取时，明确处理描述符偏移和生命周期。将真实平台发现的问题反馈到源契约，避免提前假定所有 URI 都能直接续传。

## 产品与维护取舍

直接成本是迁移对并发敏感的编排逻辑，并明确文件源资源所有权。当前收益是 CLI 业务更容易独立测试和维护，后续客户端可以复用同一套恢复、取消和结算实现。通过 CLI 与非路径测试源先检查共享边界，能减少同时引入界面、跨语言调用和平台权限问题带来的排查成本。

实施围绕现有业务流程推进。具体文件源或客户端暴露出缺失概念时再扩展模型，使分享、接收、存储访问和展示各自保持清晰。
