# Sender trace 与发送结果模型重构计划

## Implementation status

Implemented with immutable executor-owned results, bounded receipt settlement publication, distinct
protocol observation facts, native trace schema 4, and browser diagnostic schema 2. CLI projection
copies factual evidence; failed projection retains bounded raw operands and independent loss counters.
See [diagnostics](diagnostics.md) for event meanings, local response/attempt joins, and missing evidence.

## 改造目的

将发送事实的定义收敛到发送执行层，让业务逻辑与 trace 使用同一个结果来源。通过明确协议错误、单次尝试、响应发送调用及最终回执的不同语义，消除调用方手工同步字段带来的不一致。

当前 sender trace 将最后一次尝试的回执与整个发送事务的结果组合在一起，再要求嵌套的协议失败对象与外层字段相等。事务创建失败、跨通道重试、停止等待和通道迁移失败，会暴露这些字段所属范围不同的问题。诊断记录被拒绝后，现有记录又不足以还原冲突值。

改造沿用核心事实、应用投影、异步记录的职责分工。核心结果描述真实发送过程；投影负责表示转换；记录系统负责保存证据并报告自身的信息损失。

## 结果模型与职责

下列名称用于说明概念，实际命名结合现有代码统一调整。

| 概念 | 承载内容 | 负责位置 |
| --- | --- | --- |
| ProtocolErrorContent | 协议错误范围、错误码、对端重试提示 | 协议语义层 |
| SendAttemptObservation | 尝试标识、固定通道、准入状态、回执进度、传输证据、结束原因 | 单次发送尝试及回执 |
| ResponseSendResult | 是否开始尝试、调用结束原因、调用返回时的整体发送证据 | 发送执行入口与事务 |
| ProtocolObservation | 观察时间、操作及响应关联信息、对应的具体事实 | 核心观察接口 |
| ObservationRejectionEvidence | 被拒绝记录的来源、规则、实际值及信息截断情况 | 投影与记录系统 |

协议错误内容只描述协议响应的含义。发送端产生错误响应、接收端收到经过认证的错误响应，分别通过观察事件表达上下文。协议中的重试提示与本地跨通道重试资格保持独立含义。

同一个事实由一个组件负责定义。不同记录可以携带用于关联的相同标识；同一事件中的外层与嵌套内容不再独立维护两套结算结果。

## 语义安排

### 发送过程与发送证据

明确区分以下情况：

- 尚未开始任何发送尝试，例如无法取得有效路由或事务权限。
- 已进入一次发送尝试，但在交给传输层之前被拒绝或撤回。
- 调用方结束等待，发送组件仍持有处理责任，最终回执尚未产生。
- 回执已经结算，但传输结果仍然不确定。
- 传输层确认接收。

回执是否结算与发送证据是否确定是两个问题。最终回执本身也可能给出不确定结果。传输层接收不表示对端已经收到、解码或处理响应。

将 Delivered 改为明确表示传输层确认成功的名称，并迁移 SendOutcome 的转换与调用点。底层 SendAccepted 也包含无法证明传输层未接手的错误，不能直接等同于确认成功。

### 响应调用与物理结算

ResponseSendResult 表示调用返回时已经知道的事实，是不可变快照。停止等待的结果显式携带尚未结算的尝试关联，后续回执通过独立事件补充。

后续回执不会修改先前返回给业务的结果，也不会延长业务等待。分析 trace 时，可以将两个时间点的观察关联起来，区分“当时未知”与“后来得到结果”。

### 多次尝试的汇总

汇总逻辑由发送事务维护，投影不重新推断。单次尝试和事务汇总采用不同类型，避免再次把最后一次尝试当成整个事务。

| 尝试证据 | 整体发送证据 |
| --- | --- |
| 所有尝试均确定未发送 | 确定未发送 |
| 前次不确定，后次确定未发送 | 仍不确定 |
| 前次不确定，后次确认传输成功 | 至少一次确认传输成功，保留前次不确定的尝试证据 |

操作策略认为某条消息无须继续发送，与传输层证明没有发送，是不同事实。迁移现有分支时分别表达策略结束原因和发送证据，避免直接按枚举顺序合并结果。实际重试决策仍依赖现有权限、代际、取消和回执语义。

### 尝试身份

一次尝试的通道在创建观察时固定，与这次尝试的回执一起保存。后续路由选择使用单独的当前状态，迁移失败不会清空上一尝试的通道证据。

关联关系采用 session、operation、response、attempt 的层次。一个 operation 可以发送多条响应，response 使用本地序号区分，attempt 使用该响应内的序号区分。序号服务于本地诊断，不增加线上协议字段。

## 执行步骤

### 1. 定义发送结果及协议错误内容

从以下代码入口梳理实际状态和使用者：

- core/session/protocolsession/send_receipt.go
- core/session/sessionruntime/outbound_protocol.go
- core/session/sessionruntime/protocol_failure.go

将 ProtocolFailure 中的协议内容与观察上下文拆开。接收端仍能够表达“收到经过认证的协议错误”，发送端仍能够表达“尝试发送错误响应”，身份与发送状态由对应事件承载。

用具体结果类型、私有字段和按情况区分的构造入口表达未开始、调用结束、等待提前结束及回执结算。Go 的零值表示未初始化，不隐式解释为一条已经发生但结果未知的发送。

区分操作策略准入与传输层接收，沿用底层 TransportDisposition 的实际语义。跨通道重试权限、operation generation 和 lease 继续留在负责发送行为的组件内，诊断对象只复制所需事实。

把多次尝试的证据汇总提取为小型纯函数，随实现补充直接覆盖汇总语义的测试。重点围绕前次不确定、后次未发送，以及后续取得明确传输结果的组合，避免测试仅重复构造器实现。

### 2. 让发送执行入口统一产出结果

主要调整以下位置：

- core/session/sessionruntime/runtime.go 中的 senderOutbound.sendControl
- core/session/sessionruntime/outbound_protocol.go 中的事务创建与 Run
- core/session/sessionruntime/sender.go 中的相关事务调用点

由发送执行入口统合准备阶段与事务执行阶段。事务无法创建时，同样产出有语义的结果，保留响应内容和失败原因，记录尚未开始任何尝试。

Run 显式维护当前尝试及事务汇总，返回统一结果。每次尝试开始时固定通道与身份，完成或停止等待时生成快照。将路由迁移的候选通道与已经发生的尝试分离。

去掉 sendControl 在 defer 中读取 lastCompletion、当前 lane 和独立返回值来拼装发送状态的方式。正常控制流与观察逻辑从同一个执行结果读取事实。

同步迁移关键业务调用方，使资源处理读取整体发送证据：

- core/session/contentflow/handler.go：processOpen 区分 LeaseUndelivered、LeaseDetached 与保留租约；processRenew 根据是否确认传输成功决定是否 detach。
- core/session/sessionruntime/lane_attach.go：仅在整体确定未发送时撤销 grant。
- core/session/sessionruntime/runtime.go：梳理最终响应的路由释放、取消 tombstone、generation 和 lease 交接顺序。

发送证据与清理结果分别表达，清理失败作为附加原因，不覆盖已经发生的发送结果。

围绕事务无法创建、跨通道重试后失败、迁移无可用通道，以及最终响应清理等现有分支补充针对性的回归用例。

### 3. 在回执生命周期中表达后续结算

以 SendReceipt 与其内部结果对象为入口，将调用结束和物理结算两个观察边界接起来。

当调用返回时回执尚未结算，记录等待结束的原因和对应尝试身份。最终结算时，由已有回执生命周期发出关联事件，不为每次发送创建额外的等待 goroutine。

处理观察注册与回执完成之间的竞争：完成前登记的观察和完成后读取到的快照采用同一套一次性发布逻辑。事件关联使用稳定身份，记录消费方不依赖两个事件必然按某一写入顺序出现。

观察数据采用有界值快照，不持有操作权限、lease、完整消息体或整个 runtime。发布经过生产者侧的有界观察通道，避免在回执锁内执行外部观察者或文件写入。

将取消发生在准入前、发送处理期间及最终回执之后的不同路径，与已有回执测试一起梳理。记录停止或进程退出后仍没有最终证据的尝试保持未知，不补造最终结果。

### 4. 将核心观察事件改为明确的事实变体

主要调整以下位置：

- core/session/sessionruntime/protocol_operation_trace.go
- core/session/sessionruntime/operation_calls.go
- core/session/sessionruntime/protocol_failure.go

将当前同时容纳多个阶段、多个可选字段的大结构，逐步替换为按事实区分的事件入口。响应发送尚未开始、发送调用结束、尝试最终结算、收到经过认证的协议错误，各自携带本身适用的字段。

具体类型共享小型关联信息，不复制全部字段，也不引入通用事件工作流或可配置状态机。核心观察接口保持窄小，调用点可以从类型及构造入口看出事件含义。

接收端保留错误实际接收时的通道和上下文，不从稍后的 operation 当前路由回填。发送端与接收端共享协议错误内容，同时分别表达各自观察到的事实。

同步调整事件保留策略。继续控制块请求和流式响应成功路径的记录量；异常、重试以及等待提前结束时，保留解释结果所需的尝试证据。尝试历史利用现有重试数量上限，以有界形式保存。

### 5. 贯通投影与 trace 表达

主要调整以下位置：

- cmd/wind/internal/commandprojection/observer_protocol.go
- cmd/wind/internal/commandprojection/observer_mapping_protocol.go
- cmd/wind/internal/clievent/protocol_operation.go
- cmd/wind/internal/runtrace/encode_v4_session.go
- cmd/wind/internal/runtrace/payload_v4.go

投影按具体事实变体转换字段，业务状态的解释留在核心结果模型。删除协议失败对象与事件外层重复结算字段的相等规则。

保留输出格式、标识表示、事件类型与字段结构等边界检查。投影不从缺省值推断业务事实，也不把调用方停止等待重新解释为发送失败或发送结算。

协议错误内容在响应语义中出现一次。事务结果与尝试证据通过明确字段和关联层次呈现，避免复用一个 send 字段表达不同范围。

更新受影响的 schema 标识、编码器、解析器及示例。结合实际引用关系调整浏览器端共享的协议错误导出类型，保持共同概念的一致含义，各端特有的生命周期分别表达。

项目处于开发阶段，直接迁移当前调用方并删除旧类型、旧映射与重复规则。新旧两套语义不形成长期并行维护路径。

### 6. 补齐诊断记录自身的错误证据

主要调整以下位置：

- cmd/wind/internal/commandprojection 中的拒绝上下文
- cmd/wind/internal/clievent 中的 ObservationRejection
- cmd/wind/internal/cli/command_runtime_health.go
- cmd/wind/internal/runtrace 中的 observer_loss 编码

扩展现有拒绝记录，保存原始事件类型、来源位置、关联标识、具体规则和发生冲突的实际字段值。未知枚举保留原始数值，无法正常转换的标识保留便于定位的原始表示。

在投影拒绝发生时捕获值快照，避免后续状态变化改变证据。沿用已有按问题签名聚合、重复计数和容量控制机制，字段值与 operation ID 不参与无限增长的签名键。

诊断异常采用简单、独立的记录结构，不重新进入导致原事件被拒绝的语义检查。正常事件仍保有明确契约，拒绝证据明确标注自身身份，消费方不会将其解释为业务事实。

证据被截断、样本容量耗尽或异常记录自身无法写入时，保留相应计数和状态。避免通过同一个失败路径递归报告自身错误。

结合错误字段捕获、重复问题聚合和记录通道不可用等路径调整相关测试，让排查时能看到规则背后的实际冲突。

### 7. 收拢调用方与说明

沿新结果类型的引用关系整理剩余使用者，删除散落的状态拼装、重复结算字段和过时的解释性注释。注释集中说明发送责任、取消语义和不确定性保留的原因。

更新 diagnostics 说明中的事件含义、响应与尝试关联方式，以及诊断拒绝证据的阅读方式。明确 trace 中未看到某次最终结算，只能说明当前记录没有该证据。

在相关包原有测试和现有发送场景中继续观察重构影响，特别关注取消与回执的竞争、最终响应清理、重复发送策略，以及 trace 开启时的热路径开销。需要进一步修改时，沿负责该事实的组件处理。

## 推进顺序

先完成结果语义和核心类型，再将发送入口及回执生命周期迁移到统一结果来源。随后调整事件生产、投影与文件表达，最后收拢调用方、旧类型和说明。

每一步围绕完整的事实流推进，相关测试与该步实现一起调整。诊断异常的证据结构随投影改造接入，避免新旧语义交接期间只剩规则名称和丢失计数。

## 代价与设计取舍

这次改造会同时触及核心发送结果、观察类型、CLI 投影和 trace 文件表达。工作量主要来自语义迁移与调用方整理。短期类型数量可能增加，收益是新增发送分支时只需由负责执行的组件定义事实，减少跨层同步状态的负担。

行为风险集中在重试权限、取消、回执结算和资源归还之间的关系。设计上将发送结果、操作策略结束原因与资源清理结果分别表达，使观察模型调整不再依靠重新解释控制流。

尝试证据与后续结算会增加记录量。采用已有尝试次数上限、有界快照、成功热路径过滤和异常聚合来控制成本；具体分配与保留方式结合现有调用频率决定。

异步记录可能因容量、写入故障或进程退出缺少信息。业务继续独立运行，trace 明确报告自身信息损失。后续结算机制尽可能补充证据，不以阻塞业务换取表面完整。

结果模型服务于发送事实。实现保持在现有模块职责内，通过明确类型和少量纯函数承载复杂性，避免将本次重构扩展为通用事件框架。
