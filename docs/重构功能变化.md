WindShare 从“先扫描完整内容，再开始分享”重构成了“链接立即可用、按需浏览、按文件独立传输”的即时分享产品。

| 用户场景 | 主要变化 |
|---|---|
| 创建分享 | 不再递归扫描、读取、哈希或复制全部文件。relay 确认注册后立即显示链接，链接生成时间基本不受目录规模和文件体积影响。 |
| 浏览文件 | 接收方打开链接后立刻看到根目录；链接就绪后低优先级预取所选目录根的第一层，其余目录只在浏览或下载请求时扫描直接子项，未被请求的更深内容不会提前加载。 |
| 选择接收 | 可以直接选择尚未展开的目录，未来发现的后代会继承选择；树形确定后即可在最终命名/层级解析完成前显示保存选择，点击至多打开一次 picker。兼容的发现、重试和重连会把选择与已选目录保留到 commit/adoption；clean pre-cut replacement 自动复核并复用同一 picker authority。 |
| 输出产物 | `original-file` 保持单文件；`directory-tree` 保留原层级；`zip-archive` 是用户明确选择的 `store`、`complete-only` package，不再是隐藏默认，也没有 partial ZIP。 |
| 进度显示 | 内容尚未发现完时，只显示“已发现”的文件数和体积，不再把未知总量伪装成精确百分比。 |
| 预览媒体 | 支持显式点击图片预览和视频拖动定位；预览与正式下载共享范围读取和缓存，但不在创建链接时生成缩略图或分析媒体。 |
| 错误隔离 | Authenticated sender drift 终止该 source revision；本地 checkpoint 的 `revision-conflict`、`owned-object-unknown` 与 `checkpoint-invalid` 只阻塞对应 item，保留旧 bytes/ranges，独立兄弟项继续。只有 root/registry/lease/operation ownership 不确定才停止整个 operation。Collision-only partial 明确报告目标已存在，不再成为 `unexpected`；Web lifecycle 仍保留 `partial-directory`，完整产物不发布已知残缺结果。 |
| 命名与层级 | CLI 默认保存到当前目录；`-o` 始终是容器。单文件不额外套结果根，完整目录使用原目录名，部分目录使用 `<目录名>-selection`，多根使用 `windshare`。顶层冲突不覆盖/合并，而为新 operation 选择稳定后缀；同一 active operation 恢复时复用原名称。Web ZIP 沿用对应 `<结果根>.zip`。ReceiveIntent v2 在共享契约中分开 artifact requested name、logical reserved/restoration name 与 physical filesystem name；CLI 保存行为不变，普通 native output 的 logical name 与 physical name 相同。 |
| 浏览器拒绝名称 | Compatible-name 与恢复工具仅属于 Web FSA。Web FSA 只在真实 non-creating native lookup 抛出 `TypeError` 时改用 `<readable-prefix>.windshare-<token>`，不按名称、扩展名或平台猜测，也不自动切换 ZIP/CLI。当前 Windows 会先创建 restoration script + sidecar 再继续；其他平台在 target mutation 前安全停止。 |
| 续传与保存 | Native destination 的四项能力全部成立才可 resumable；发送端 handle 在 grace 后释放也不改变 revision identity，重新打开的 source evidence 完全相同即可用新 lease 继续既有 ranges，无法验证可稍后重试，证据变化则失效且不发布 replacement revision。只有 safe publish + crash cleanup 时以 warning-once 进入 live-only，下一次 `get` 使用新名称重下 selection。Web 在本地 capability 与 exact checkpoint 都可恢复时，页面刷新后建立新 session 并继续；Workspace 完整封存后仍可进入 `waiting-to-save` 并再次 handoff。FSA compatible output 在 restoration 前可按 ledger 继续；运行脚本恢复原名后，该 output 不再支持 browser resume。portable stream 等无法可靠恢复的输出会明确降级。 |
| 完成状态 | Native CLI 的 command result 与 persistent operation state 分离；retryable failure 不创建终态历史。Web 受控 target 确认 commit 才是 `published`；`browser-handoff` 只能到 `download-started`。Compatible output 只有在 quiescent settlement 验证 terminal sidecar 后才显示 “Completed/Partial with compatible names”；失败时保留 pending local catch-up，不提前宣称成功。Workspace 在创建 OPFS entry 前先写 activation journal，reload 只恢复 exact marked candidate，无法确认 ownership 时进入 attention。 |
| 停止与清理 | Native `resume discard` 只删除 identity-matching unfinished WindShare-owned state，永不删除 final 或陌生对象。Web post-cut settlement/detach 失败会保留 owner 并提供 cleanup retry；重试只执行未完成阶段，完成前不允许新接收/继续。旧 state 不迁移、不双读，只由 certified cleaner 清理。 |
| 浏览器能力 | Workspace route 不再依赖可选 quota estimate；缺失、失败或无效 estimate 记为 unknown，FSA/portable 也不受影响，实际写入仍逐阶段检查容量。 |
| 已保留任务 | Continue、Save、Download again、Discard/Delete 开始后会显示 busy，并暂时禁用选择、产物和所有 retained controls；每条成功、失败、取消或 reload 路径都会清除 busy。 |
| 连接体验 | 浏览目录默认走已经建立的 relay；点击预览或下载时 relay 立即可传内容，P2P 同时在后台协商并做有界恢复。P2P 超时、重试、断开或耗尽不会打断健康 relay。 |
| 安全与隐私 | 链接和 `#` 后的密钥可以分开复制，通过不同渠道发送；密钥会立即从地址栏移除，不上传或记录。receiver 可以为页面刷新保留本地 capability，缺少时也可由用户本地输入。relay 看不到文件名、内容和协议中明示的精确文件大小，但仍能观察流量和时序。 |
| 停止分享 | 当前仍是纯在线分享：发送端明确停止或退出后，现有下载终止，新接收方无法加入。当前重新执行分享会生成新链接，尚未实现同一链接的内容 refresh；协议不排除未来提供该体验。尚未支持发送端退出后链接继续有效。 |

用户需要特别理解的行为边界：

- 根层预取仅有一层且不递归；其余目录在接收方第一次按需浏览或下载时分别“定格”，并不是点击分享那一刻得到整棵目录的统一快照。
- 目录定格后新增或修改的内容不会自动同步；源文件发生变化可能导致对应文件下载失败，需要重新分享。
- 发送端不会为保证稳定下载而偷偷制作完整文件副本；因此分享期间文件可能被锁定，本机修改也可能中断该文件传输。
- Workspace ZIP 与 portable download 在请求任何文件内容前完成 exact preparation 和容量检查；超限时零 content request。`WorkspaceBudgetV1.peakOwnedBytes` 是 `uniqueRawBytes`、`packageBytes`、`peakTemporaryBytes` 与 `durableMetadataBytes` 的 checked sum；quota estimate 只是 optional observation，不是 reservation。
- 当前 Web 可继续或安全丢弃 `resumable-receive`/`resumable-package`；Continue 由 output-owned executor 复核 exact preparation 或 sealed package evidence。`waiting-to-save` 保存、workspace `download-started` 再次 handoff、expiry 与 cleanup 也由 output authority 执行。
